## Drift

**ok — 0 offenders across all steps, 0 unscoreable.**

Every step scored its frozen entries as byte-identical against the previous
step. The comparison that makes this worth anything: **the same replies, replayed
with `incremental: false`, produce 3 drift offenders** (Grondulf, once per
step). The model's replies re-word Grondulf on every step; under incremental he
is never asked for and never moves, under full rebuild he is rewritten each
time. That is the mechanism doing the only thing it exists to do.

Two notes on how drift is scored, because the basis changed in this issue:

- `basis: frozen-set` uses the run's own `planIncrementalRun` verdict on whose
  source changed. This is the correct basis and is used whenever it exists.
- `basis: source-ref` is the original PHA-2732 proxy — "this entry's citations
  end at or before the last slice boundary". It is only a proxy, and it has a
  real false-positive mode: an entry cited at message 2 that the story is
  *still* discussing at message 20 scores as source-unchanged, so every honest
  update to it reads as drift. In the full-rebuild comparison above, Pemberly is
  flagged for exactly this reason on an update that is genuinely warranted. It
  is kept as the fallback because a full rebuild has no frozen set, which is the
  mode where real drift is expected, and the false positive is pinned as a
  documented test rather than hidden.

Also fixed here: `checkDrift` used to `continue` past any entry it could not
reason about and still report `ok`. It now returns an `unscoreable` count, so an
`ok` over an empty sample is visible instead of reassuring. (The related
`stmbAutoSourceRef` parsing gap was resolved independently by PHA-2722, which
moved both checks onto `extractProvenanceRanges`.)

**ok.** A hand-edit applied before step 2 was still byte-identical in the book at

## Idempotence

**ok at every step.** After each step, a second full pass over the *same* slice
left the book byte-identical.

This is a stronger question than check 5 (`checkZeroWritesOnRerun`), which only
asks what the pinning stage decided to do. A step can legitimately "write" an
entry whose content happens to match and still be idempotent; a step that
re-words one entry is not, whatever it reported.

## Cost — bracketed, not measured

| | input tokens | output tokens | write calls |
|---|---|---|---|
| incremental (floor: model ignores rule 6) | 6050 | 534 | 4 |
| incremental (ceiling: model obeys rule 6) | 6050 | 400 | 4 |
| full rebuild replay | 6029 | 534 | 7 |
| **saved, floor** | **−0.3%** | **0%** | **42.9%** |
| **saved, ceiling** | **−0.3%** | **25.1%** | **42.9%** |

Reading this honestly, in the order that matters:

1. **Input tokens are 0.3% WORSE, not better.** Under one-shot generation the
   whole transcript goes into the prompt either way; incremental adds the
   `[settled — do not re-emit]` tags on top. The issue predicted this and it is
   what happened. Input and output are never summed in this report, because a
   summed number would hide it.

2. **The output-token saving is a bracket, not a measurement.** A canned reply
   set replays what was recorded regardless of what the prompt says, so a
   scripted model *cannot* demonstrate prompt compliance — hence the 0% floor.
   The 25.1% ceiling comes from re-running with a scripted model that does obey
   the tag. A real model lands somewhere between, and **only a live run
   establishes where**. Anyone quoting 25.1% as the result is quoting the
   ceiling.

3. **The 42.9% write-call saving is the one number here that is guaranteed.** It
   comes from `dropFrozenEntries` enforcing rule 6 on our side rather than
   trusting the model to follow it.

4. Token counts are `char/4` estimates, not billed usage.

**None of this is the reason to want incremental runs.** The reason is the drift
row: an entry nobody asked the model to rewrite cannot come back re-worded. That
is the guarantee `applyProvenancePinning` explicitly could not make on its own,
because it compares against freshly generated prose that is byte-identical only
by luck.

## Reproduce

```
node eval/runIncrementalReplay.js                       # summary + report.json
node --test oneShotIncremental.test.js                  # the mechanism
node --test eval/rewriteAcceptanceIncremental.test.js   # the harness
```

Point `--fixture` at a real transcript to run it against one; the fixture shape
is documented in `runIncrementalReplay.js --help`. Note that message ids must be
1-based, because `extractProvenanceRanges` requires `start >= 1`.
